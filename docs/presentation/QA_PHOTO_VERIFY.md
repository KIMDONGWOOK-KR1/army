# 성과발표 Q&A 대비: 정찰원 정문 사진 판정

11/14 성과발표에서 정찰원 '불꽃문양 사진으로 찾기'에 질문이 나올 때 쓸 답변 자료다. 발표 자료·Q&A 목록을 만들 때 그대로 가져다 쓴다.

- 기준: 2026-11-06 평가(`photo-verify`, main `f6ab3f0`). **11/10 정문 추가 촬영 뒤 수치를 갱신한다.** 갱신 전에는 아래 수치만 쓴다.
- 기준값(임계값)·기준 사진은 정답 자료라 여기에 적지 않는다. 발표에서도 말하지 않는다.

## 한 줄 설명
정찰원이 불꽃문양을 찍으면, 서버가 미리 넣어 둔 기준 사진 몇 장과 비교해 같은 대상인지 판정한다. 먼저 사진 전체 분위기로 1차 비교하고(DINOv2), 비슷하면 세부 특징점을 하나하나 맞춰 본다(ALIKED + LightGlue). 따로 AI 모델을 학습시키지 않아서, 새 장소도 기준 사진 3~5장만 있으면 붙일 수 있다.

## 써도 되는 수치
| 항목 | 값 | 말할 때 |
|---|---|---|
| 정답 사진 통과 | 306 / 306 (밤 220 + 낮 86) | "사전 평가에서" |
| 오답 사진 거절 | 39 / 39 (비슷한 조형물·안내판 27, 하늘·바닥 등 11, 밤 1) | "사전 평가에서" |
| 밤 → 낮 | 밤에 찍은 기준 사진 5장만으로 낮 정답 86장 모두 통과 | 강점으로 |
| 세부 일치점 | 정답 최저 146개 vs 오답 최고 29개 | 2단계 판정 근거 |
| 응답 시간 | 서버(2 vCPU) p95 약 1.7초, 첫 요청(콜드 스타트) 약 7초 | |
| 앱 업로드 경로 | 앱이 줄여 올린 사진(1600px)으로도 정답 86/86, 오답 38/38 | |

## 말하면 안 되는 것
- "정확도 100%", "오답률 1% 이하 검증". 오답이 39장뿐이라 통계적으로 입증하지 못한다(0/39의 95% 상한은 약 7.5%). 또 기준값을 같은 자료로 정했으므로 결과가 낙관적이다.
- "배포 완료", "어디서나 동작". 지금은 노트북 판정 서버에 연결한 개발 화면에서 동작한다.

## 예상 질문과 답변

**Q. 정확도가 어느 정도인가?**
A. 정문 사전 평가에서 정답 사진 306장은 모두 통과했고, 비슷한 조형물·안내판을 포함한 오답 39장은 모두 거절했다. 다만 거점 한 곳의 사전 평가이고 오답 표본이 적다. 오답 사진을 늘려 정식 평가하는 것이 다음 단계다.

**Q. 날씨·시간대가 바뀌면?**
A. 밤에 찍은 기준 사진만으로 낮 사진을 모두 맞혔다. 아직 강한 햇빛·역광·비 오는 날은 시험하지 않아 추가 촬영으로 확인한다. 어둡거나 흔들린 사진은 '다시 찍기'로 안내하고 실패로 세지 않는다.

**Q. 비슷한 다른 조형물을 찍으면?**
A. 전체 모양만 보면 정답과 오답 점수가 비슷하게 나오는 경우가 있었다. 그래서 2단계로 세부 특징점을 맞춰 본다. 세부 일치점은 정답이 최소 146개, 오답이 최대 29개로 크게 갈린다.

**Q. 계속 틀리면 게임이 막히나?**
A. 실패할 때마다 힌트(실루엣 선명하게 → 위치 단서)를 준다. 3번 실패하면 사진 단계만 넘어가고 뒤 문제는 그대로 풀어서 진행이 막히지 않는다. 사진 실패에 따른 점수 감점은 아직 확정하지 않았다.

**Q. 인터넷 사진이나 화면에 띄운 사진을 찍으면?**
A. 사진 판정만으로 화면 속 사진을 구분하지는 않는다. 현장 도착은 GPS 판정이 맡고, 사진은 현장에서 대상을 찾아보게 하는 미션 장치다. 부정행위 방지는 확장 과제로 둔다.

**Q. 왜 직접 AI 모델을 학습하지 않았나?**
A. 장소마다 수백 장을 모아 학습하면 장소를 늘리기 어렵다. 사전학습 모델을 그대로 쓰고 기준 사진 몇 장과 비교하는 방식이라, 새 거점은 기준 사진 3~5장과 기준값 조정만 하면 된다.

**Q. 실제로 배포돼 있나? 서버 비용은?**
A. 판정 서버는 Docker 이미지와 Cloud Run 배포 문서까지 준비했고, 시연은 노트북 서버로 한다. 2 vCPU 서버에서 p95 약 1.7초다. 요청이 있을 때만 켜지는 방식이라 첫 요청은 약 7초 걸린다.

**Q. 찍은 사진은 저장하나? 개인정보는?**
A. 사진은 판정에만 쓰고 저장하지 않는다. 촬영 안내도 사람 얼굴이 크게 나오지 않는 구도로 한다.

**Q. 다른 거점(용봉관·추모의 벽)은?**
A. 같은 판정 서버에 기준 사진과 기준값만 추가하면 된다. 이번에는 정문 한 곳에서 먼저 검증했다.

**Q. 왜 Cloudflare 같은 무료·경량 서버에 올리지 않았나?**
A. 비용보다 서버 크기 문제다. 판정 서버는 PyTorch 모델을 올린 Python 컨테이너라 메모리를 약 0.9GB 쓴다. Cloudflare Workers는 메모리 128MB 제한이 있는 JavaScript 실행 환경이라 이 서버를 그대로 올릴 수 없다. 같은 이유로 Supabase Edge 안에서 돌리는 방법도 제외했고, Hugging Face Spaces 무료 티어는 쓰지 않으면 휴면에 들어가 행사 중 가용성을 보장하기 어려워 제외했다. 그래서 컨테이너를 그대로 올리고 요청이 있을 때만 켜지는 Cloud Run(서울)을 골랐다. 비용은 월 1만 원 예산 알림과 최대 인스턴스 2대로 관리한다.

## 발전 가능성: 배포와 운영

발표 '발전 가능성' 파트와 "배포는 어떻게 할 건가" 질문에 쓴다. 아직 하지 않은 일이므로 **계획**으로만 말한다.

| 지금 한계 | 해결 계획 | 판단 기준 |
|---|---|---|
| 판정 서버가 노트북에서만 동작 | 준비된 Docker 이미지를 Cloud Run 서울 리전에 배포하고, 앱(Supabase Edge)이 공유 키로 호출하게 연결 | 실제 폰으로 정문 판정 성공 |
| 첫 요청(콜드 스타트) 약 7초 | 행사 시간대에만 최소 인스턴스 1대를 켜 두고 끝나면 0으로 되돌림. 시작 시 CPU 부스트 사용 | 행사 중 첫 판정도 2초 안팎 |
| CPU 응답 속도(현재 p95 약 1.7초)가 클라우드에서 느려질 수 있음 | Cloud Run에서 직접 재어 2초를 넘으면 같은 코드를 GPU 서버리스(Modal)로 옮김 | 클라우드 실측 p95 2초 이하 |
| 동시 접속이 늘면 대기 발생 | 인스턴스당 한 장씩 판정하고, 사람이 몰리면 인스턴스를 자동으로 늘림(상한 조정) | 여러 팀 동시 진행 시 시간 제한 초과 없음 |
| 비용 미측정 | 월별 청구 내역으로 행사 1회당 비용을 기록해 운영 기관 예산 근거로 씀 | 행사 단위 비용 산출 |

**한 줄 답변:** "판정 서버는 컨테이너로 준비돼 있어 Cloud Run에 올리기만 하면 됩니다. 행사 시간에만 서버를 켜 두어 첫 요청 지연을 없애고, 클라우드 속도가 부족하면 같은 코드를 GPU 서버로 옮기는 경로까지 마련해 두었습니다."

## 남은 한계 (내부 공유용)
- 거점 1곳, 오답 39장. 기준값을 같은 자료로 정해 낙관적이다
- 자동 보정은 오답이 적으면 기준값을 잘못 정해 쓰지 않는다. 지금은 데이터를 보고 수동으로 정한 기준값을 쓴다
- 실제 폰으로 정문에서 처음부터 끝까지 시험하지 않았다(11/10 예정, `photo-verify/docs/FIELD_TEST_GATE.md`). Android 기종도 아직 시험하지 않았다
- 사진 찾기 화면은 개발 서버 전용이다(배포판·Supabase 모드에서는 보이지 않음). Cloud Run 배포 전
- 실제 판정 모드에서도 정문 화면 문구가 시연용 문구로 나온다(`web/lib/scout-photo/sites.ts`). 시연 영상 전에 고친다
